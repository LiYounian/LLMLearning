字节级 BPE（BBPE）：从此再无"未知字符"

GPT-2 的关键一招：不在 字符 上做 BPE，而是在 UTF-8 字节 上做。基础词表固定为 256 个字节，天底下任何字符——中文、emoji、乱码——都是这 256 个字节的组合，于是彻底消灭了 [UNK]。[5]

被这些模型使用： GPT-2/3/3.5/4/4o Qwen 全系 DeepSeek V2/V3 LLaMA-3 Kimi K2 · RoBERTa · Mistral(Tekken)

① 先回答一个常见疑问：字符怎么变成数字再统计？

直觉是对的——先把字符转成编码（字节），再在编码上做统计合并。现代大模型用的编码不是 ASCII，而是它的超集 UTF-8：ASCII 字符占 1 个字节（值 0–127），中文通常占 3 个字节，emoji 往往占 4 个字节。下面这个可视化器让你亲眼看到这个转换：

字节级 BPE 的输入，就是上面那一串 0–255 的整数。BPE 的合并统计发生在这串字节上：高频的字节组合（比如英文里 t 后面常跟 h）被合并成新 token；生僻字虽然拆成多个字节，但每个字节都在 256 基础词表里，永远有得表示。

🎯 这一招解决了什么
在字符级 BPE 里，基础词表 = 语料里出现过的所有字符。世界上有十几万个 Unicode 字符，训练时没见过的生僻字/新 emoji 就会变成 [UNK]。改到字节级后，基础词表恒为 256，覆盖一切字节序列——OOV 问题在数学上被彻底消除，代价只是生僻字会多占几个 token。[8]

② GPT-2 的一个小技巧：byte-to-unicode 映射

直接把原始字节喂给 BPE 有个工程麻烦：有些字节是不可打印的控制符（如换行、空格），在词表文件、日志里显示混乱。GPT-2 于是做了一个可逆的"字节→可见 Unicode 字符"映射：把 0–255 里那些"不好看"的字节，一一映射到一段安全可打印的 Unicode 码点上（比如空格字节 0x20 映射成 Ġ）。

  • 这纯粹是表示层的化妆，不改变信息，可逆。你在 GPT tokenizer 里看到 Ġthe 这种带怪符号的 token，就是这么来的——Ġ 代表"前面有个空格"。
  • 好处：整个词表和 merge 规则都能用可打印文本存储，处理管线干净统一。

③ 一个常被忽略的细节：空格归属

字节级 BPE 通常把空格并到后一个词的开头。所以 " the"（带前导空格）和 "the"（不带）是两个不同的 token。这解释了很多"玄学"现象：

  • prompt 结尾多打/少打一个空格，可能让续写质量不同。
  • 数数字母、做字符级操作时模型容易出错——因为它看到的是 Ġstrawberry 这样一个整块，而不是一个个字母。
🈶 中文 / CJK 的代价
一个汉字 UTF-8 占 3 字节。如果词表里没为常见汉字/词组学到合并规则，一个汉字可能被切成 2–3 个 token，中文文本的 token 数会明显多于等长英文。这正是后来 Qwen、DeepSeek 等中文强相关模型把词表做大、专门为中文优化合并的动因——去 切词对比页 亲眼看 GPT-2 把一句中文切成 54 个 token、DeepSeek 只要 15 个。

④ 中文为什么"吃亏"：亲手在字节上跑 BPE（可交互）

一个汉字 UTF-8 占 3 个字节。在字节级 BPE 里，模型看到的起点是字节，要先把一个字的 3 个字节合并成"整字 token"，再把整字合并成"词 token"。下面这个教学玩具让你亲手体验：看着"深度学习"从 12 个字节 token 一步步被合并。你会发现——要把它压到 1–2 个 token 需要相当多的合并规则，这正是中文/CJK 需要更大词表的直观原因。

💡 结论
英文常用词往往几个字母就成一个 token（词表花费小）；中文每个字先要"耗掉"若干合并才能成为整字，再成词。同样大的词表，能覆盖的中文词就更少 → 中文要达到与英文相当的压缩率，词表必须更大、且要专门喂中文语料。这就是 Qwen/DeepSeek 把词表做到 12–15 万、并重点优化中文合并的原因（对比见 切词对比页）。

⑤ 进阶：一个 token 会"跨字符边界"吗？（真实实测）

常见疑问：一串字里，会不会出现"前一个字的后半字节 + 后一个字的前半字节"被合成一个 token的现象？答案是——会，而且我用真实 Qwen 分词器抓到了。

🔬 实测证据（Qwen2.5）
韩语 토크나이저 里，Qwen 产出一个 token，它的字节 = 토 的最后一个字节 + 크 的第一个字节——不含任何一个完整字符，正是"前字尾 + 后字头"。印地语（天城文）里也大量出现。脚本见 scripts/probe_crosschar.py。

为什么会：BPE 合并纯按"字节对频次"驱动，对字符边界毫无感知；正则预切分只挡住"跨词/跨空格/跨标点"的合并，同一段同种文字内部，跨字符边界的相邻字节对照样是合并候选。只要它够高频就会被合并。

为什么中文里几乎看不到（深度学习模型… 实测 34 字全部边界对齐）：中文语料多，Qwen 先把每个汉字自己的 3 字节合成"整字 token"（字内字节对超高频），再合成词，于是都卡在字/词边界。而覆盖不足的文字（此处韩语/印地语）没学全整字合并，裸字节对就赢了 → 冒出跨界碎片 token。

🧭 一句话
原理上永远可能（BPE 是"边界盲"的）；实践中取决于训练覆盖——高覆盖语言 token 边界对齐，低覆盖文字会出现"前字尾+后字头"的跨界 token。
